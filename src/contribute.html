01 / START SMALL

Choose a contribution

Browse existing issues first to avoid duplicating work. For a major feature or new language runtime, open an issue to discuss the approach before writing code.

  • Documentation: clarify instructions or explain an unsupported construct.
  • DSA examples: add a supported example with known outputs and edge cases.
  • Accessibility: improve keyboard navigation, labels or mobile layouts.
  • Runtime fixes: include a minimal reproduction and a regression test.

JavaScript core is the only working runtime today. Other languages, async tracing and framework lifecycle visualizations are planned. Never label simulated output as real execution.

02 / YOUR OWN COPY

Fork and run locally

Sign in to GitHub and fork the repository. Install Node.js 22 or newer, then run these commands. Replace YOUR_USERNAME with your GitHub username.

git clone https://github.com/YOUR_USERNAME/tracecode.git
cd tracecode
git remote add upstream https://github.com/ascebiswajit/tracecode.git
git switch -c fix/describe-your-change
npm install
npm start

Open http://localhost:3000. The editable website lives in src/; dist/ is generated by the build.

03 / MAKE IT WORK

Make and verify your change

Keep each pull request focused on one problem. Update documentation when behavior changes and add regression tests for interpreter fixes.

npm run check
npm run build
npm test
  • Check desktop and mobile layouts for interface changes.
  • Try keyboard navigation and make sure controls have clear labels.
  • Preserve execution limits and escape code/output before rendering it.
  • Do not commit secrets, credentials, private code or generated build files.

Tests live in tests/. Examples live in src/examples.mjs. Runtime and trace details are in the architecture guide below.

04 / SHARE YOUR CHANGE

Open a pull request

git add src/ tests/ docs/
git diff --cached
git commit -m "Describe the problem your change solves"
git push -u origin fix/describe-your-change

Stage only the files you changed; adjust the paths above if needed. On GitHub, open a pull request with base: ascebiswajit/tracecode → main and head: your fork → your feature branch.

Start a pull request ↗

Choose compare across forks, then select your fork and branch. GitHub may initially show “nothing to compare” until you select your changes.

Include in your PR

  • The problem and why the change helps.
  • An issue reference, such as Closes #123, if applicable.
  • Expected behavior and any remaining limitations.
  • Checks you ran and screenshots for visual changes.

The repository provides a PR template automatically. For unfinished work, use a draft pull request.

05 / REVIEW & MERGE

Work with the maintainer

CI checks run on pull requests. Respond to feedback, update your branch and push again; the same PR receives your new commits. The maintainer reviews and merges accepted changes.

Anyone can view, fork and propose changes. Public access does not give everyone permission to push directly to main. Contributions use the MIT license. Be respectful, welcome beginners and keep discussions focused on the work.

For suspected security vulnerabilities, follow the security policy instead of publishing exploit details in a public issue.
